# Daily Plan — концепция проекта

## Идея

Минималистичная «записная книжка» для быстрого фиксирования задач на день.
Вызывается глобальной горячей клавишей, открывается компактным окном поверх всех
окон. Никаких проектов, списков, заголовков — только поток задач текущей даты.

Целевая платформа: **macOS** (стилизация под стандартное приложение «Заметки»).

## Экраны и функциональность

### 1. Quick-capture окно (главный экран)

- Вызывается по глобальному шорткату (напр. `Cmd+Shift+D`, настраиваемый).
- Компактное окно, `alwaysOnTop`, без панельного мусора; повторное нажатие
  шортката скрывает окно.
- Содержимое: список задач **текущего дня**. Каждая задача — параграф с номером
  (`1. Сходиться в банк…`, многострочный текст допустим).
- Крупная кнопка **「+»** внизу: по нажатию разворачивается многострочное поле
  ввода; Enter/потеря фокуса фиксирует запись.
- Клик по существующей задаче → она переходит в режим редактирования inline
  (только для задач своего дня).
- Все записи создаются с меткой даты «сегодня». **Удаления задач нет вообще** —
  история неизменяема, «лишние» задачи комментируются.

### 2. Календарь

Отдельный экран (то же окно в другой вкладке/состояние) с двумя режимами.

**Год** — типичная сетка 4×3 (12 месяцев). В ячейках-днях отображается
**количество задач** за этот день (бейдж/цифра, чем больше — тем насыщеннее
фон, как heatmap).

**Месяц** — вертикальный список задач, сгруппированных по дням
(заголовок-дата + задачи под ним).

**Перенос задачи (только в режиме «Месяц»)** — задачу из дня A можно перенести
в день B. Перенос не дублирует текст, а создаёт в дне B **ссылку на день A**:
одна строка с предпросмотром текста оригинала (первые ~40 символов + `…`).
Клик по ссылке открывает исходную задачу (переход/окно просмотра). Оригинальная
задача остаётся в дне A неизменной. **Комментарии всегда привязаны к самой
задаче (оригиналу)** — общая лента на все «вхождения», отображается на экране
просмотра задачи.

**Пометка переноса цветом**: запись-перенос в списке дня рендерится с
**оранжевым фоном** (в светлой и тёмной теме — свои оттенки), чтобы перенесённое
сразу отличалось от «родных» задач. Оригинальная задача, у которой есть хотя бы
один перенос, помечается аккуратно — ненасыщенный индикатор (например,
оранжевая точка/полоса слева), без фона: она своего дня, а гость — ссылка.
Признаком служит `is_transfer` (см. модель данных).

### 3. Комментарии и просмотр задачи

- Любой задаче можно оставить комментарий (даже старой). Все комментарии —
  лента одной задачи; у переносов общая лента с оригиналом.
- Число комментариев (бейдж) показывается у задачи и у её записей-ссылок —
  всегда по оригиналу.
- Если комментариев ≥ 1 — задачу можно открыть в **отдельном окне просмотра**
  (текст задачи + лента комментариев).
- Правила редактирования (задачи не удаляются никогда — только правка своего
  дня и комментарии):
  | | своей даты | чужой даты | запись-перенос (ссылка) |
  |---|---|---|---|
  | Редактировать текст | ✅ | ❌ только комментарий | ❌ (клик = переход к оригиналу) |
  | Комментировать | ✅ | ✅ | ✅ |
  | Перенести в другой день | ✅ | ✅ | ❌ |

### Визуальный стиль

Как macOS Notes: системный шрифт SF, мягкие скругления, «чернильная» типографика,
светлая/тёмная тема по системной, полупрозрачный фон (vibrancy) где уместно,
минимум chrome-элементов.

## Стек

| Слой | Решение | Комментарий |
|---|---|---|
| Каркас | **Tauri v2** (Rust backend) | лёгкое always-on-top окно, нативные API |
| Фронтенд | Vite + **Svelte** | лёгкий бандл, нативная близость к стилю Notes |
| Глобальный шорткат | `tauri-plugin-global-shortcut` | требует Accessibility permission на macOS |
| БД | **SQLite** через `tauri-plugin-sql` (rusqlite под капотом) + миграции из Rust | см. обоснование ниже |
| Стиль окна | `alwaysOnTop`, `decorations`, `shadow`, vibrancy | конфигурация в `tauri.conf.json` |

**Про БД:** SQLite — правильный выбор, ничего лучше для локального
однопользовательского приложения нет (одна запись — сам файл в
`app_data_dir`, транзакции, индексы по дате, резервное копирование = копия
файла). Альтернативы рассмотрены и отклонены: flat-file/JSON — нет атомарности
и запросов по датам; DuckDB — аналитическая, избыточна; sled — нет SQL-запросов,
экосистема слабее.

Два варианта доступа к SQLite:
1. `tauri-plugin-sql` — DB напрямую из фронтенда, миграции объявляются в Rust.
   Быстрый старт, минимум кода. **Рекомендуется для MVP.**
2. `rusqlite` + `#[tauri::command]` — репозиторий-слой на Rust. Больше контроля
   (транзакции, валидация правил «редактировать только свой день» на backend).
   К нему мигрируем, если плагин упрётсяся в ограничения.

## Модель данных

```sql
-- задачи: без заголовков, нумерация = порядковый номер внутри дня
CREATE TABLE tasks (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  day         TEXT NOT NULL,              -- 'YYYY-MM-DD' (локальная дата создания)
  position    INTEGER NOT NULL,           -- порядок внутри дня (номер задачи)
  text        TEXT NOT NULL,              -- для записи-переноса: '' (текст у оригинала)
  source_id   INTEGER REFERENCES tasks(id), -- NULL = обычная задача; иначе перенос-ссылка
  is_transfer INTEGER GENERATED ALWAYS AS (source_id IS NOT NULL) VIRTUAL,
                                        -- булев признак переноса, вычисляется БД сам
  created_at  TEXT NOT NULL,              -- ISO-8601 timestamp
  updated_at  TEXT NOT NULL
);
CREATE INDEX idx_tasks_day ON tasks(day, position);
CREATE INDEX idx_tasks_source ON tasks(source_id);

-- комментарии: всегда к оригиналу задачи (для переноса task_id = source_id),
-- можно к любой задаче, в т.ч. старой
CREATE TABLE comments (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id     INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  text        TEXT NOT NULL,
  created_at  TEXT NOT NULL
);
CREATE INDEX idx_comments_task ON comments(task_id);
```

Правило «свой день» вычисляется на лету (`day == today(local)`), отдельного
флага «редактируемости» нет — дата сама по себе и есть статус.

## Технические детали

- **Номер задачи** — `position` внутри дня; удаления нет, так что номера
  стабильны и перенумерация не требуется.
- **Запись-перенос** — строка в `tasks` с `source_id` и пустым `text`, признак
  `is_transfer` (`source_id IS NOT NULL`) отдаёт сама БД как generated column —
  отдельный флаг-колонка не нужен, рассинхрон исключён. Рендерится как ссылка
  на день оригинала с оранжевым фоном и предпросмотром `substr(text, 1, 40)`
  исходной задачи. Добавление комментария к ссылке автоматически резолвится в
  `source_id` — лента одна на оригинал. В календаре «Год» переносы считаются
  задачами своего дня (отражают активность), но повторный перенос ссылки запрещён.
- **Полуночь**: если окно открыто и дата сменилась — список должен
  переключиться на новый день (старые задачи уходят в календарь).
- **Отдельное окно просмотра задачи**: Tauri multi-window — окно `label:
  task-{id}`, создаётся по клику на бейдж комментариев.
- **Поведение quick-capture окна**: показ-фокус-клавиатура сразу в input по
  шорткату; Esc — скрыть окно (не закрыть процесс: приложение живёт в трее /
  фоновом режиме).
- macOS-специфика: глобальные шорткаты требуют запроса Accessibility-прав;
  иконка в Dock необязательна (`ActivationPolicy::Accessory` для «агентного»
  поведения).

## MVP (порядок разработки)

1. Каркас Tauri + окно quick-capture (always-on-top, шорткат, скрытие по Esc).
2. SQLite + миграции, CRUD задач текущего дня, список + кнопка «+», inline-редакт.
3. Календарь: режим «Месяц» (группировка по дням) → режим «Год» (сетка 4×3 с
   количеством задач).
4. Комментарии: бейджи, форма комментария, окно просмотра задачи.
5. Переносы: действие «перенести в день» в режиме месяца, запись-ссылка с
   предпросмотром, переход к оригиналу.
6. Полировка стиля Notes: темы, типографика, анимации, vibrancy.
